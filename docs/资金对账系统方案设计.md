# 资金对账系统建设方案（完整版 v2.0）

> 银行流水与财务凭证对账核销 · 余额勾稽 + 明细核销双层架构
> 面向月末集中对账场景 · 对账码优先核销 · 分组轧差 · 差异工单闭环 · 审计全留痕
> 2026 年 6 月

本方案在 v1.0 思路稿基础上，对照真实银企对账场景补齐了六项缺口：

| # | v1.0 的缺口 | v2.0 的补齐 |
|---|------------|------------|
| 1 | 只有明细核销，没有余额对账层 | 新增「余额勾稽 + 银行存款余额调节表」（第三章） |
| 2 | 缺数据完整性与质量校验 | 新增导入防重、余额连续性校验、红冲/作废凭证处理（第二章） |
| 3 | 对账范围与口径未定义 | 新增科目↔账户映射、内部互转识别、无凭证银行项目归类（第二章） |
| 4 | 缺核销生命周期管理 | 新增反核销、期间管理、重跑保护（第六章） |
| 5 | 跨月结转缺会计语义 | 未达账项标准四分类，与调节表同源（第三、七章） |
| 6 | 工程实现形态未定义 | CLI + SQLite，标准模板 CSV/Excel 输入，AI 可插拔（第九、十章） |

---

## 一、背景与目标

资金系统的银行流水与财务共享系统的会计凭证之间需要逐期完成对账核销。当前以月末集中对账为主，主要痛点：

1. 自动匹配率不足导致大量人工干预；
2. 拆分合并交易的匹配复杂；
3. 差异处理过程中跨部门反复沟通、责任不清、月月重复。

**目标**：建立一套以确定性规则为主、AI 辅助兜底的对账核销机制，核心包括四层：

- 余额勾稽前置校验 + 银行存款余额调节表产出（v2.0 新增，会计标准交付物）；
- 以对账码为强关联键的优先核销链路；
- 面向拆分合并的分组轧差判定逻辑；
- 让差异自动流转闭环的工单机制。

**设计原则**：对账主链路由规则引擎承担（快、准、可审计），AI 仅用于规则覆盖不到的尾部疑难项；所有核销与挂账全程留痕，自动与人工动作可清晰区分；**金额校验永远是确定性的，AI 不替代金额轧平**。

## 二、数据模型、口径与质量校验

### 2.1 对账范围与口径（v2.0 新增）

- **科目↔账户映射**：维护账户主数据表（账号、户名、开户行、对应科目编码如 1002.01、币种）。凭证按科目编码归属到银行账户后参与该账户的对账；映射不上的凭证在导入时报错，不进入对账。
- **内部账户互转**：对手方账号命中本方账户主数据的银行流水标记 `is_internal=1`。互转两侧各自有凭证，正常参与本账户对账，标记仅用于报表区分与异常排查。
- **无凭证对应的银行项目**（利息、手续费、银行代扣）：不是"匹配失败"，而是标准的**未达账项——银行已收/已付、企业未入账**，进入调节表并开工单要求补凭证。
- **多币种**：本期范围限人民币账户；外币账户按币种隔离对账与汇率折算差异归类列入二期。

### 2.2 统一中间表字段

| 数据侧 | 关键字段 | 说明 |
|--------|---------|------|
| 银行流水侧 | 账号、交易日期、入账日期、金额、收付方向、对手方户名、对手方账号、摘要/附言、银行流水号、对账码 | 以（账号+银行流水号）唯一，对账码为关联键 |
| 财务凭证侧 | 凭证号、分录行号、凭证日期、业务日期、科目编码、银行账号、金额、借贷方向、往来对象、摘要、关联业务单号、对账码、凭证状态 | 以（凭证号+分录行号）唯一；按**分录行**粒度对账 |
| 余额侧（新增） | 期间、账号、银行对账单期初/期末余额、账面期初/期末余额 | 余额勾稽与调节表的输入 |

### 2.3 字段归一化规则

- **方向**：银行收/付与财务借/贷按固定映射表转换为统一方向标识 IN/OUT（银行存款科目：借=IN、贷=OUT），映射表配置化。
- **金额**：以「分」为单位整数存储（Decimal 解析 + 四舍五入到分），彻底避免浮点误差造成的假差异。
- **日期**：统一 ISO 格式，区分交易日期与入账/记账日期，供时间容差判断。
- **户名**：去空格、全半角统一、去常见公司后缀干扰，并维护简称别名表供模糊匹配。

### 2.4 数据质量校验（v2.0 新增，导入即拦截）

| 校验项 | 规则 | 不通过的处理 |
|--------|------|-------------|
| 流水防重 | （账号+银行流水号）唯一；文件内、库内双重去重 | 跳过并计数，导入报告列明 |
| 凭证防重 | （凭证号+分录行号）唯一 | 同上 |
| 作废凭证 | 凭证状态=作废的行不进入对账 | 跳过并计数 |
| 红冲凭证 | 状态=红冲的行以负向金额参与组内轧差（与原凭证自然对冲） | 正常导入，打 `is_reversal` 标 |
| 必填与格式 | 金额/方向/日期可解析，账号在主数据中 | 整行拒绝，报告列明行号与原因 |
| 余额连续性 | 期初 + Σ(签字金额) = 期末，两侧各自勾稽（见 3.1） | `check` 命令输出告警，提示流水缺漏/重复 |

## 三、余额对账层（v2.0 新增）

真实对账是"先总后细"的两层结构。余额层有两个作用：**前置发现数据缺漏**（流水不全时先修数据，而不是产生一堆假差异工单）；**产出审计要求的银行存款余额调节表**。

### 3.1 余额勾稽（对账前置校验）

对每个账户、每个期间：

```
银行侧：对账单期初余额 + Σ(本期流水签字金额) ?= 对账单期末余额
财务侧：账面期初余额   + Σ(本期凭证签字金额) ?= 账面期末余额
（签字金额：IN 取正、OUT 取负；红冲行取反）
```

任一侧勾稽不平 → 数据不完整告警（提示缺漏或重复），建议先修复数据再跑明细对账。

### 3.2 未达账项标准四分类

明细核销后仍未匹配的记录，按方向落入标准四类（这四类同时是调节表的四个调节项，也是差异工单跨月结转的会计依据）：

| 分类 | 来源 | 调节方向 |
|------|------|---------|
| 银行已收、企业未收 | 未匹配银行流水，方向 IN | 账面余额 + |
| 银行已付、企业未付 | 未匹配银行流水，方向 OUT | 账面余额 − |
| 企业已收、银行未收 | 未匹配凭证，方向 IN | 对账单余额 + |
| 企业已付、银行未付 | 未匹配凭证，方向 OUT | 对账单余额 − |

### 3.3 银行存款余额调节表

```
调节后对账单余额 = 对账单期末余额 + 企业已收银行未收 − 企业已付银行未付
调节后账面余额   = 账面期末余额   + 银行已收企业未收 − 银行已付企业未付
平衡校验：调节后对账单余额 − 调节后账面余额 ?= Σ(本期容差核销累计差额)
```

容差核销（手续费/尾差）产生的累计差额作为独立调节项列示；残差不为零时报表给出「存在未解释差异」红色告警——这是对整个对账结果的总闸门校验。

## 四、分层匹配策略

按匹配置信度从高到低分层执行，每一层匹配成功的记录即锁定，不再进入下一层。

| 层级 | 匹配方式 | 适用场景 | 置信度 | 自动化 |
|------|---------|---------|--------|--------|
| 第 1 层 | 对账码精确匹配 / 分组轧差 | 存在对账码（主力链路） | 高/中 | 自动核销 |
| 第 2 层 | 多字段组合精确匹配（金额+方向+账号+日期，优先同对手方） | 无对账码、有强字段；**对账码错/缺的兜底救回** | 高 | 自动核销 |
| 第 3 层 | 一对多 / 多对一凑数匹配（subset-sum） | 拆分合并、码缺失 | 建议 | 建议核销，需人工确认 |
| 第 4 层 | 模糊匹配（相似度+别名表，AI 语义兜底） | 摘要/户名不规范的尾部 | 建议 | 建议核销，需人工确认 |

**AI 介入边界**：仅第 4 层语义判断与第 3 层凑数归属判断使用 AI，且 AI 不替代金额校验——金额必须精确轧平，AI 只辅助判断归属与生成说明。

## 五、对账码分组轧差判定逻辑

精髓：有码优先信任整组轧平、轧不平再下钻子集、并以置信度划清自动与人工的边界。

### 5.1 分组与预处理

按对账码将两侧流水各自归组，组内计算签字金额汇总并做方向校验：

```
对每个对账码 code：
    银行侧：bank_sum = Σ(签字金额)，bank_cnt = 笔数
    财务侧：fin_sum  = Σ(签字金额)，fin_cnt  = 笔数（红冲行负向）
    方向校验：银行侧组内出现正负混合（非红冲所致）→ 挂「方向异常」工单，整组跳过
```

### 5.2 轧差判定决策树

```
diff = bank_sum − fin_sum
├─ diff == 0
│   ├─ bank_cnt==1 且 fin_cnt==1 → 【1:1 精确核销】高，自动
│   ├─ 一侧1笔、另侧多笔        → 【1:N 分组核销】高，自动
│   └─ 两侧均多笔              → 【M:N 分组核销】中，自动+抽样复核
├─ 0 < |diff| <= 容差阈值
│   └─ 【可容差核销】差额挂「手续费/尾差」调节项，中，自动+留痕
└─ |diff| > 容差阈值
    ├─ 组内可轧平子集（先等额对对碰，再 subset-sum）→ 【部分核销】
    │       已轧平部分核销，剩余挂「未达/缺漏」工单
    └─ 无法轧平 → 【整组挂账】进差异工单（原因码初判：金额错记/缺单）
```

### 5.3 关键判定参数（配置化）

| 参数 | 建议值 | 说明 |
|------|--------|------|
| 金额容差 | ±0.50 元（可配） | 覆盖尾差与零星手续费 |
| subset-sum 上限 | 单组 ≤ 8 笔 | 防组合爆炸，超限转人工 |
| 第 2/3/4 层时间窗 | ±5 天（可配） | 有码时不作硬约束，仅异常提示 |
| 模糊匹配阈值 | 相似度 ≥ 0.85 | 低于阈值不出建议 |

### 5.4 拆分合并的处理

- **情况 A（各笔均带同一对账码）**：直接整组轧差，不做笔级配对。推动业务端拆分时透传对账码，使该场景最大化。
- **情况 B（对账码缺失或不全）**：第 3 层在「同账号 + 同方向 + 同对手方 + 时间窗」约束内 subset-sum 凑数，设组合上限；凑数成功仅标记**建议核销**，需人工确认后才算正式核销，审计上不作强匹配。

示例：同一对账码下银行 3 笔（100/200/300）对财务 2 笔（100/500），全组 diff = 600 − 600 = 0，直接整组核销；若 diff ≠ 0，才下钻子集，先核销、剩余挂账。

### 5.5 置信度与自动化边界

| 置信度 | 判定情形 | 处理方式 |
|--------|---------|---------|
| 高 | diff=0 且结构简单（1:1、1:N）、第 2 层精确 | 自动核销，记「自动」 |
| 中 | M:N、容差核销 | 自动核销 + 强制留痕 + 抽样复核标记 |
| 建议 | subset-sum 凑数、模糊匹配 | 生成建议核销，**人工 confirm 后生效** |
| — | 整组挂账 | 不自动，进差异工单 |

## 六、核销生命周期与期间管理（v2.0 新增）

- **核销锁定**：进入 matched/suggested 状态的记录被锁定，后续批次不再参与匹配，杜绝重复核销。
- **反核销**：`unmatch` 撤销一笔核销（自动或已确认均可），关联记录释放回未匹配；撤销动作记录操作人、时间、原因，原核销记录保留为 `cancelled` 状态——**只追加不删除**。
- **期间管理**：期间有 open/closed 状态。关账后该期间拒绝导入、匹配、确认、反核销等一切写操作；需要调整必须先重开期间（留痕）。
- **重跑保护**：同一期间重复执行对账为**增量重跑**——已核销（自动/人工/已确认）记录全部保留，仅未匹配记录重新进入分层匹配。人工成果永不被重跑冲掉。
- **建议核销待办**：subset-sum/模糊匹配产生的建议核销停留在 pending 状态，`confirm` 确认生效、`reject` 退回释放，处理人与时间留痕。

## 七、差异工单流转设计

目标：把月末的「反复沟通」变成「工单自走」。开单即带全上下文 + AI 归因、按原因码自动派单、状态机与看板让流转透明、跨月结转避免重复劳动。

### 7.1 工单的产生（带齐上下文）

凡未自动核销的差异，系统自动开单（同一记录已挂在未关闭工单上的不重复开单），附带完整上下文：

```
工单 = {
  差异ID、对账批次、对账码,
  银行侧明细 [流水号/金额/日期/摘要],
  财务侧明细 [凭证号/金额/科目/摘要],
  差异金额、差异类型(系统初判原因码),
  归因建议(AI 生成的一句话),
  建议责任方、建议处理动作
}
```

### 7.2 原因码与自动派单（配置化路由表）

| 原因码 | 含义 | 责任方 | 建议处理动作 |
|--------|------|--------|-------------|
| FEE_INTEREST | 手续费/利息未入账 | 财务共享 | 补记凭证 |
| BANK_ONLY | 银行已收/付、财务未记 | 财务共享 | 补凭证 |
| FIN_ONLY | 财务已记、银行未到（在途） | 资金/业务 | 核实在途，跨月结转 |
| MISSING_DOC | 漏记/缺单 | 业务部门 | 补提单据 |
| AMOUNT_MISMATCH | 金额错记（同码两侧轧不平） | 财务共享 | 红冲调整 |
| CODE_ERROR | 对账码错/缺 | 业务部门 | 修正对账码 |
| DIRECTION_ERROR | 方向异常 | 财务共享 | 核实方向映射 |

新增原因码只改配置、不改代码。原因码初判由规则完成（关键词、结构特征），AI 生成一句话归因写入工单。

### 7.3 工单状态机

```
待派单 → 待处理 → 处理中 → 待复核 → 已解决
                    ↘ 退回(待复核→处理中，必填原因) ↗
        待处理/处理中 → 已结转 → (次月复对成功自动)已解决
```

每次状态变更记录操作人、时间、备注。看板按责任方、状态、账龄聚合；挂账超 N 天自动列入催办清单。

### 7.4 跨月结转闭环

- 本月未解决且判定为「在途/跨期」（FIN_ONLY 等）的差异，执行 `carryover` 标记结转；
- 次月对账时结转记录**自动带入并优先**与新流水复对；
- 一旦匹配成功，工单自动闭环并回溯标注「X 月差异，Y 月解决」。

### 7.5 解决闭环回写

工单处理后（如财务补齐凭证并导入），重新触发对账：能轧平则自动核销，**所有关联记录已全部核销的开放工单自动关闭**，形成「差异 → 处理 → 复核 → 核销」完整闭环。

## 八、审计留痕设计

每一笔核销/挂账/撤销/状态变更均落一条可追溯记录，自动与人工动作清晰区分，数据只追加不删除。

| 留痕字段 | 说明 |
|---------|------|
| 核销批次号 | 某次对账执行的唯一标识 |
| 匹配方式 | 对账码1:1 / 分组轧差 / 多字段精确 / 金额凑数 / 模糊 / 人工 |
| 匹配置信度 | 高（自动）/ 中（自动+复核）/ 建议（需人工确认） |
| 关联明细 | 参与本次核销的全部银行流水 ID 与凭证行 ID |
| 操作人 / 时间 | 自动记 system，人工记工号 |
| 差异原因码 | 挂账时必填 |
| 撤销留痕 | 反核销的操作人、时间、原因，原核销记录保留 |

**审计要点**：建议核销（AI/凑数推断）必须留有人工确认痕迹；调节表残差校验作为整体对账正确性的总闸门。

## 九、AI 模型分工与接入方式

绝大部分对账逻辑由确定性规则承担，AI 调用集中在尾部约 5%–15% 的疑难项。

| 模型 | 承担环节 | 选择理由 |
|------|---------|---------|
| Haiku 4.5 | 第 4 层语义模糊匹配、凑数归属判断 | 量大但单次简单，速度快、成本低 |
| Sonnet 4.6 | 差异归因、一句话说明、派单建议（主力） | 需一定推理，性价比均衡 |
| Opus 4.8 | 跨期、复杂多对多疑难账分析 | 量小但难，需强推理能力 |

**接入方式（已确认）**：AI 定义为可插拔 Provider 接口。配置 `ANTHROPIC_API_KEY` 时真实调用 Claude API；未配置或调用失败时自动降级到规则 Provider（字符串相似度 + 别名表 + 原因码规则模板），**任何环境都能完整跑通**。AI 输出仅作为说明与建议写入工单/核销记录，不改变金额判定。

## 十、工具实现设计（CLI + SQLite）

### 10.1 形态与技术栈

- Python ≥ 3.11，核心零第三方依赖（sqlite3/csv/decimal/argparse/tomllib 全为标准库）；
- 可选依赖：`openpyxl`（读 .xlsx 模板）、`anthropic`（真实 AI 调用）；
- 数据落 SQLite 单文件库（`recon.db`），天然满足留痕、重跑、审计查询需求；
- 报告输出：终端摘要 + HTML 报告 + CSV 明细（差异清单/调节表/核销明细）。

### 10.2 输入模板（CSV，UTF-8，表头中文；同名 .xlsx 亦可）

1. `accounts.csv`：账号、户名、开户行、科目编码、币种 —— 账户主数据与科目映射
2. `bank.csv`：账号、交易日期、入账日期、金额、方向、对手方户名、对手方账号、摘要、银行流水号、对账码
3. `vouchers.csv`：凭证号、分录行号、凭证日期、业务日期、科目编码、金额、借贷方向、往来对象、摘要、关联业务单号、对账码、凭证状态
4. `balances.csv`：账号、对账单期初余额、对账单期末余额、账面期初余额、账面期末余额
5. `aliases.csv`：原始名称、标准名称（模糊匹配别名表）

### 10.3 命令一览

```
fince-recon init                                    初始化数据库
fince-recon accounts import accounts.csv            导入账户主数据
fince-recon aliases import aliases.csv              导入别名表
fince-recon period open|close|list 2026-06          期间管理
fince-recon import bank|vouchers|balances <file> --period 2026-06
fince-recon check --period 2026-06                  余额勾稽 + 数据质量校验
fince-recon run --period 2026-06                    执行分层匹配（增量重跑安全）
fince-recon matches list|show --period 2026-06      核销记录查询
fince-recon confirm|reject <match_id> --by 工号     建议核销的确认/退回
fince-recon unmatch <match_id> --by 工号 --reason   反核销
fince-recon tickets list|show|move|board            工单查询/流转/看板
fince-recon carryover --from 2026-06 --to 2026-07   跨月结转
fince-recon report --period 2026-06 --out out/      调节表 + HTML 报告 + CSV 导出
```

### 10.4 核心库表

`periods / accounts / bank_txns / vouchers / balances / batches / matches / match_links / tickets / ticket_links / ticket_events / audit_log / aliases`。金额一律整数分；记录状态 `unmatched → suggested → matched`，核销状态 `auto / pending / confirmed / cancelled`。

## 十一、验收场景（随工具附带演示数据）

演示数据生成器覆盖以下场景，`demo.sh` 一键端到端跑通两个月：

1. 对账码 1:1 精确核销；2. 同码 1:N 拆分核销；3. 同码 M:N 整组轧平；
4. 容差核销（差额 ≤ 0.5 元挂尾差）；5. 同码轧不平→组内部分核销+剩余挂账；
6. 无码多字段精确匹配；7. 对账码录错→第 2 层兜底救回；
8. 无码拆分 subset-sum → 建议核销 → 人工确认；
9. 户名不规范 → 别名表+相似度（AI 兜底）→ 建议核销；
10. 银行手续费无凭证 → FEE_INTEREST 工单 → 财务共享；
11. 月末在途（财务已记银行未到）→ 结转次月 → 次月流水到达自动复对、工单自动闭环；
12. 红冲凭证组内对冲；13. 文件内重复流水防重；14. 内部账户互转标记；
15. 余额勾稽通过 + 调节表平衡校验（含容差调节项）。
